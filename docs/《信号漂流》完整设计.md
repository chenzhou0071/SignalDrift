**一、项目概述**

**1.1 项目定位**

PC 端 2D 1v1 多人联机信号博弈游戏，无实体单位、无怪物、无空中信号对冲；依靠发射能量信号争夺地图节点，利用黑洞、反射中立地形形成策略对抗，主打资源扩张与地形博弈。

**1.2 技术栈**

- 客户端：Unity2D，仅负责输入采集、画面表现，无任何战斗逻辑、物理、判定运算
- 后端：Golang，TCP 网关 + 大厅服务 + 房间战斗服务三层架构
- 存储：MySQL 持久化玩家数据；对局全部数据仅存房间内存，对局结束销毁
- 通信：自研二进制 TCP 协议，内置粘包分包、会话、限流、消息路由

**1.3 后端架构核心亮点**

1.  网关、大厅、房间三层完全解耦，工业级游戏服务器分层设计
2.  全服务端权威：信号飞行、引力、反射、占领、能量、胜负全部服务端计算，彻底防作弊
3.  战斗逻辑与数据库 IO 完全隔离，内存异步事件队列处理对局结算，不阻塞战斗 Tick
4.  全配置驱动，战斗、物理、经济参数全部 JSON 配置，无硬编码，平衡迭代成本低
5.  单房间独立 Goroutine，对局结束自动回收内存，无内存泄漏

**二、全局基础对局规则（固定 1v1）**

**2.1 节点统一占领数值模型（核心）**

1.  地图所有节点（普通 / 反射 / 黑洞）初始占领值 OccupyVal = 0，黑洞、反射为中立地形，对双方信号效果完全一致。
2.  信号命中节点修改规则：

- 玩家 1 发射信号命中：OccupyVal += 信号剩余BasePower
- 玩家 2 发射信号命中：OccupyVal -= 信号剩余BasePower

1.  节点归属判定：

- OccupyVal 0：归属玩家 1
- OccupyVal < 0：归属玩家 2
- OccupyVal = 0：中立无归属

1.  权重统计（每 Tick 统一计算）

- 玩家 1 总占领权重 = 所有 OccupyVal 0 的节点数值求和
- 玩家 2 总占领权重 = 所有 OccupyVal < 0 的节点数值取绝对值求和
- 全局总权重 = 玩家 1 权重 + 玩家 2 权重

**2.2 能量产出规则**

1.  产出公式（每 Tick 结算）  
    玩家本Tick新增能量 = 自身总占领权重 × 节点基础产出值 + 己方信号塔固定产能
2.  限制规则

- 玩家能量存在全局存储上限，溢出部分直接丢弃
- 黑洞节点不提供任何产能，仅作地形博弈点位
- 反射节点产能低于普通节点，取舍博弈

1.  信号塔设定

- 双方开局各拥有 1 座专属无敌信号塔，无法被攻击、无法被占领
- 信号塔持续提供固定基础能量，不受地图节点占领情况影响

**2.3 胜负双判定机制**

1.  即时胜利判定  
    己方总占领权重 ÷ 全局总权重 ≥ 配置获胜比例（0.6），对局立刻结束，该玩家获胜。
2.  时限判定  
    对局运行至最大时长限制时，对比双方总占领权重：

- 权重更高者获胜
- 双方权重相等，判定平局

**2.4 地形通用约束**

1.  黑洞、反射仅作用信号飞行物理，不区分玩家阵营，双方信号受同等效果影响
2.  无空中信号碰撞抵消逻辑，信号之间互不干扰

**三、信号完整物理体系**

**3.1 双独立数值模型**

1.  RemainRange 剩余动力（飞行寿命）

- 决定信号最大飞行距离，飞行持续消耗
- 反射碰撞固定扣除动力里程
- 动力≤0 触发坠落，信号生命周期结束

1.  BasePower 信号强度（争夺节点威力）

- 决定修改节点占领值的幅度
- 随飞行距离缓慢衰减
- 反射仅消耗动力，不削弱威力；黑洞直接湮灭信号，威力完全作废

**3.2 能量转信号计算逻辑**

玩家输入投入能量 InputEnergy，服务端强制校验：

1.  投入能量 ≥ 最低发射门槛
2.  投入能量 ≤ 玩家当前持有能量  
    校验通过后计算初始属性：

- 初始射程动力 = InputEnergy × 能量射程系数
- 初始威力 = InputEnergy × 能量威力系数

**3.3 坠落完整流程**

1.  信号剩余动力≤0，停止飞行、引力、反射运算
2.  判断坠落坐标碰撞：

- 命中节点碰撞范围：使用当前剩余 BasePower 修改节点 OccupyVal
- 未命中任何节点：信号直接作废，投入能量全部亏损

1.  全网广播坠落、节点占领值变更事件

**四、特殊中立地形节点规则**

**4.1 黑洞节点**

1.  引力生效范围：仅距离≤1 格产生引力，超出无效果
2.  引力向量规则：距离越近拉力越大；距离 1.0 拉力为 0，距离 0 拉力最大
3.  多黑洞区域引力向量叠加计算，持续扭曲信号飞行轨迹
4.  信号触碰黑洞核心极小半径直接湮灭，所有投入能量全部亏损
5.  无能量产出，仅战略地形

**4.2 反射节点**

1.  信号碰撞触发镜面反弹，重新计算飞行方向向量
2.  每次反射固定扣除配置里程动力，多次反射可耗尽远程信号
3.  反射不衰减信号威力，仅缩短飞行寿命
4.  能量产出低于普通节点

**4.3 普通节点**

地图经济核心，单位产能最高，无任何飞行干扰，基础扩张目标

**五、客户端操作流程与通信协议**

**5.1 完整操作流程**

1.  鼠标点击己方无敌信号塔，选定发射源
2.  UI 弹出能量选择滑块，区间：最低发射能量～玩家当前持有能量
3.  玩家确认投入能量数值
4.  点击地图任意坐标，确定信号初始飞行方向
5.  客户端组装 TCP 指令发送至网关，本地不做任何模拟、计算、预判
6.  等待服务端持续推送信号飞行、反弹、坠落、节点占领、能量变化表现数据

**5.2 客户端发包协议字段（二进制）**

| --- | --- |

| SourceNodeID | 发射源信号塔唯一 ID |
| TargetPosX | 点击坐标 X，仅用于计算飞行方向向量 |
| TargetPosY | 点击坐标 Y |

**六、服务端房间 Tick 步进模拟完整流程**

房间固定帧率 Tick 循环，每帧执行顺序：

1.  **信号物理运算**

- 根据速度向量移动所有飞行信号，持续消耗剩余动力、缓慢衰减威力
- 遍历全部黑洞，对范围内信号叠加引力向量，扭曲飞行轨迹；触碰核心直接销毁信号
- 检测信号与反射节点碰撞，反弹速度向量、扣除固定动力；动力不足直接触发坠落

1.  **坠落结算**

- 遍历所有动力耗尽信号，执行坠落逻辑，命中节点则修改节点 OccupyVal

1.  **权重与能量结算**

- 遍历全地图节点，分别统计玩家 1、玩家 2 总占领权重
- 按公式计算双方本 Tick 新增能量，叠加至玩家能量池，超出上限则截断

1.  **胜负判定**

- 计算双方占领占比，达到 60% 立即结束对局、进入结算流程
- 判断对局时长是否到达最大时限，超时则对比权重判定胜负

1.  **全网广播**  
    推送所有信号状态、节点最新占领值、双方当前能量、双方总占领权重给两个客户端

**七、后端全套业务体系**

**7.1 TCP 网关（纯网络层，无业务逻辑）**

1.  自研二进制协议，实现粘包分包、消息长度校验
2.  会话 Session 管理，记录玩家在线状态、连接凭证、断线重连 Token
3.  多层限流安全防护

- IP 全局限流：单 IP 每秒总包数上限，超限断连并临时拉黑
- 发射指令专项限流：单玩家每秒最大发射请求次数，超限丢弃指令并告警
- 重复包幂等过滤：消息携带序列号，过滤循环重复发包

1.  应用层心跳断线检测

- 客户端 5 秒推送一次心跳包
- 服务端 15 秒未收到心跳标记玩家离线，开启 30 秒重连倒计时

1.  消息路由：将合法消息分发至大厅服务 / 对应房间服务

**7.2 大厅服务（承载全部局外厚业务）**

1.  账号体系：注册、登录、密码哈希存储、身份校验
2.  玩家档案与 ELO 段位系统

- 存储基础 ELO 分数、历史最高段位
- 对局结束异步更新积分，胜利加分、失败扣分、平局小幅调整

1.  好友系统

- 添加 / 删除好友、在线状态同步、好友对局邀请

1.  ELO 智能匹配池（仅 1v1）

- 按段位分差匹配对手
- 匹配等待每 30 秒自动放宽分差阈值
- 等待超时无匹配对手，支持手动取消匹配，无惩罚

1.  背包道具系统（配置驱动）

- 道具对局内小幅修正射程系数、抗引力、反射动力损耗
- 大厅持久化存储，房间仅读取道具 ID，逻辑解耦

1.  内存异步事件队列  
    仅保留三类异步任务，完全隔离战斗线程与数据库 IO：
2.  对局结束更新玩家 ELO 积分
3.  对局历史数据批量入库
4.  玩家活跃度统计上报

**7.3 房间战斗服务**

1.  单对局独立 Goroutine，对局结束销毁协程，释放全部内存数据
2.  仅管理对局内存数据：地图节点、玩家能量、飞行信号、对局计时、占领权重
3.  全程不操作 MySQL 数据库，所有持久化工作交由异步队列完成
4.  断线重连完整逻辑

- 断线 30 秒缓冲期，玩家占领节点、能量、飞行信号全部保留不变
- 凭重连 Token 恢复房间，服务端下发当前全量战斗状态
- 超时未重连：在线玩家直接判定胜利，执行对局归档
- 离线玩家无 AI 接管，无法发射新信号，仅保留现有版图

**7.4 房间集群负载均衡与生命周期管理**

1.  房间服务实例启动向注册中心上报负载（在线房间数、CPU / 内存使用率）
2.  大厅分配新房间时优先选择负载最低的服务节点
3.  服务优雅缩容：标记排空状态，不再接收新对局，存量对局结束后关闭进程
4.  过载保护：单实例房间达到上限，拒绝新建房间，自动分流至其他节点

**7.5 运维监控与告警系统**

1.  全链路指标采集

- 网关：在线连接、包吞吐、限流拦截次数、断线数量
- 大厅：匹配队列长度、好友请求 QPS、登录请求量
- 房间服务：活跃房间数、单 Tick 平均耗时、每秒发射指令总量

1.  告警阈值

- 单房间 Tick 运算耗时过高，卡顿告警
- 网关大量恶意发包、高频限流触发安全告警
- 数据库写入队列堆积、IO 阻塞告警
- 房间服务负载率超过 90%，扩容提醒

1.  分级日志  
    INFO：匹配、对局创建、结算、上下线；WARN：限流、断线、配置异常；ERROR：服务异常、数据库写入失败
